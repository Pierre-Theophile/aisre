# The live run, 2026-09-16

This is FR-050 (b) and SC-010: both reference feeders pointed at a disposable Kubernetes
cluster running a demo application with tracing enabled, and the graph built live compared with
the graph built from a recording of the same run. It is also where
`fixtures/baseline-topology-01`, `fixtures/rollout-regression-02`, `fixtures/config-change-01`
and `fixtures/feeder-gap-01` come from (T058, T063, T066, T067, T082).

It is written up in full, including the things that did not work, because the runbook in
[`deploy/kind/README.md`](../../deploy/kind/README.md) had never been executed end to end and
four of its instructions turned out to be wrong or incomplete. Those are fixed; the rest of
this file is the evidence.

## What did not work, and what was changed

### 1. `--record` records no events at the default batch size

`aisre feed k8s --record DIR` filled `DIR/payloads/` and never created `DIR/events.jsonl`.

`record.Emitter` writes a line per event *the graph answered for*, and `write()` returns early
when the result is nil — which is exactly what a batching emitter returns, because it has not
asked yet (`pkg/feeder/record/events.go`). `--batch-size` defaults to
`emit.DefaultBatchSize = 100`. So the documented recording command produces payloads, no
events, no warning, and a directory that looks like a recording.

**Changed:** `deploy/kind/README.md` now passes `--batch-size=1` in both the short way and the
Recording section, and says why.

**Recommended, not done here (outside this task's files):** `docs/connectors/writing-a-feeder.md`
§9 shows `record.Emitter(connectEmitter, dir)` with no mention of batch size, while §8 explains
the nil result two pages earlier without connecting the two. Either `record.Emitter` should
fail loudly when it is wrapping a batching emitter, or `--record` should force a batch size of
1. A connector author following §9 will produce an empty recording.

### 2. A recording needs a graph that has never seen it

The first attempt restarted the feeders against the database the previous attempt had already
filled. Feeder event ids are pure functions of the objects they describe (FR-018, FR-020), so
every event came back `DUPLICATE_NOOP` — which the recorder correctly does not write down,
producing, again, payloads with no events.

**Changed:** `deploy/kind/README.md` says to give each recording its own database. Each of the
four recordings below used a fresh one (`live_baseline`, `live_rollout`, `live_config`,
`live_gap`).

### 3. `--record` into a non-empty directory corrupts the recording

`events.jsonl` is opened `O_APPEND`, but payload files are numbered per kind from `000001` on
every run and written with `os.WriteFile`, which truncates. A second run into the same
directory therefore overwrites the first run's payloads while the index still points at them,
and the recording replays the wrong bytes with no error.

This matters because `scenarios/feeder-gap.sh` restarts the Kubernetes feeder with the same
command line — including its `--record` flag — which is precisely the corrupting case.

**Changed:** `deploy/kind/README.md` documents it. The gap recording below was made into a
second directory and merged.

### 4. Recording an OTLP stream is too heavy to ship

telemetrygen exports one OTLP request per generated trace, and `--record` writes one file per
request. At the committed `--rate=2` / `--rate=1` that measured **363 payload files and 3.4 MB
per minute** — about 6000 files and 20 MB for one twelve-minute recording, four times over.
That is not a fixture anybody can review, and reviewing recorded goldens as a pull-request diff
is how this project asserts they are right (`fixtures/README.md`).

telemetrygen has no flag that batches: `--interval` paces the generator, not the exporter. This
was tried (`--interval=30s`, applied to all eight containers) and changed the rate not at all.

**Changed:** `deploy/kind/otel-demo/minimal/traffic.yaml` now runs the four busy edges at
`--rate=0.5` and the four quiet ones at `--rate=0.05`. That is ~66 files and ~230 KB a minute,
and it straddles a published weight-class boundary (`pkg/feeder/weight.go`: class 1 is < 0.1
rps, class 2 is < 1 rps), so the recorded `calls` edges carry two distinct classes rather than
one. The file has the arithmetic.

**What it costs.** The hand-authored fixture spans weight classes 4, 3 and 2. Class 4 needs
≥ 10 rps on one edge, which is ≥ 5 exports a second from one container; no choice of rates
reaches it and stays shippable while one payload file is one export. Restoring the full class
range needs payload compaction in `pkg/feeder/record` — many OTLP requests per file, or a
length-delimited stream — not another change to the overlay.

### 5. `aisre feed k8s --record` writes Secret material to disk

**This is the one worth acting on.** `internal/feeders/k8s/informers.go` `RedactSecret` replaces
every value in `.data` with a SHA-256 of itself before the payload is built, and the events are
clean — no material reaches the graph. But it copies metadata untouched, and `kubectl apply`
stores the entire original manifest, `stringData` included, in the annotation
`kubectl.kubernetes.io/last-applied-configuration`. Every Secret in a cluster that was ever
`kubectl apply`-ed therefore carries its own cleartext in an annotation, and `--record` writes
it to a file.

`deploy/kind/rbac/README.md` currently states the opposite — "no material reaches the graph or a
recorded fixture" — and for the graph it is right; for the recording it is not.

The demo Secret is `not-a-real-token-disposable-demo-cluster` on a cluster that was deleted, so
nothing was leaked here. `internal/feeders/k8s`'s own `TestNoSecretMaterialInTheCorpus` caught
it on the recorded corpus, which is the test working exactly as intended.

**Done here:** the annotation was stripped from the four recorded `secrets/*.json` payloads —
which is what a fixed `RedactSecret` would have produced, so the replayed events are unchanged
and the feeder conformance tests pass on the sanitized bytes.

**Not done here (`internal/feeders/k8s` is outside this task's files), and it should be:**
`RedactSecret` must drop `kubectl.kubernetes.io/last-applied-configuration` — and, for size and
noise as much as safety, `managedFields`. Until it does, anyone recording a real cluster
commits secrets.

### 6. The Kubernetes feeder's valid times follow payload arrival order

Two shuffle checks failed, and they are the same bug.

**At the feeder boundary** (`testkit.Shuffle` over `testdata/kind-shop`): the 32 payloads of a
real informer list arrive microseconds apart, and the feeder stamps the initial list's
`valid_at` — and the extent of the checkpoint that closes it — from the arrival time of
whichever payload it saw first. Permuting them inside the declared 60 s reordering window moves
every initial-list fact by a few microseconds. The synthetic corpora never showed this because
every payload in them carries the same whole-second time.

```
in-order   checkout-config  validAt 2026-09-16T09:38:32.509162Z
shuffled   checkout-config  validAt 2026-09-16T09:38:32.509178Z
```

**At the graph** (`fixture verify` over `rollout-regression-02`): an `exposed-via` edge is
stamped with the arrival time of the *Service* payload that created it, while the workload it
points at is stamped with the arrival time of the *Deployment* payload. In that recording the
Service for `shop/payments-db` arrived 2 µs before its Deployment, so the edge asserts a valid
time earlier than its own endpoint's. In arrival order the projector sees the node first and
nothing happens; shuffled, the edge lands first and the projector materializes an empty
placeholder version of `payments-db` for those 2 µs:

```
in order:  valid=[09:53:09.749193Z, )              name="payments-db"  props={...}
shuffled:  valid=[09:53:09.747114Z, .749193Z)      name=""             props={}
```

The final state is identical; the valid-time *history* is not, and FR-021 and FR-048 say it
must not depend on arrival order. `fixtures/baseline-topology-01` has zero edges whose valid
time precedes their endpoint's, which is why it verifies — not luck, but not a guarantee
either: whether a run trips this depends on the order the informers happen to deliver in.

**Done here:** both are visible and named rather than hidden.
`internal/feeders/k8s/feeder_test.go` has `TestConformanceKindShopShuffle`, skipped with the
reason; `internal/query/fixture_golden_test.go` has a `shuffleExceptions` table with one entry.
`rollout-regression-02` ships *because* it is the reproduction.

> **Corrected 2026-09-17: fixed.** `TestConformanceKindShopShuffle` runs, and
> `shuffleExceptions` is empty. The fix is the one this section predicted — one initial list,
> one valid-time stamp — taken from the informers' sync marker and given FR-011's unknown start
> rather than a guessed instant, with the placeholder an edge mints for an endpoint it reaches
> first inheriting that flag (`internal/feeders/k8s/feeder.go`,
> `internal/projector/upsert_edge.go`).

**The fix**, in `internal/feeders/k8s`: one initial list, one valid-time stamp, taken from the
sync marker the informers already push, and every fact derived from the list — nodes and edges
alike — asserted at that instant.

### 7. `scenarios/feeder-gap.sh` could not produce the scenario it documents

Two bugs, both found by running it.

**It exited before doing anything.** Under `--keep-feeder` the script prompts and calls
`read -r _`. With `set -e` and no terminal — `< /dev/null`, and every CI job, which is where
T082's nightly run lives — `read` returns non-zero at EOF and the script ends there, silently,
having deleted nothing. Fixed: `read -r _ || true`, twice, with the reason in a comment.

**It restored the Service before the feeder came back.** The order was: stop the feeder, delete
`svc/checkout`, sleep, restore it, restart the feeder. A reconnecting feeder has no memory — it
lists the namespace and reports what is there — so by the time it looked, the Service was back.
There was nothing missing to notice and nothing to retract. The script could not produce the
outcome its own table in `deploy/kind/README.md` promised.

Fixed: the feeder now comes back **into the absence**, is given `RELIST_SECONDS` (default 30)
to finish its initial list, and only then is the Service restored. The README's table row says
so too.

### 8. The Kubernetes feeder does not reconcile on reconnection, and cannot see its own gap

With the script fixed, the scenario ran properly: feeder down 11:50:10, `svc/checkout` deleted
11:50:11, feeder back 12:00:16 with the Service still absent. It emitted **one** event:

```json
{"eventId":"k8s:kind:ckpt:20260916T120016Z","sourceCheckpoint":{
  "extentFrom":"2026-09-16T12:00:16.550757Z","extentTo":"2026-09-16T12:00:16.550757Z",
  "note":"initial informer list complete for namespace shop"},"sourceId":"k8s:kind"}
```

Two things are missing from it, and both are what T067 asks a fixture to prove.

**No retraction.** `k8s.service=shop/checkout` and the `exposed-via` edge to it are still valid
`[10:43:42Z, ∞)` in the graph, ten minutes after the object stopped existing. The feeder lists
and upserts; it never diffs the list against what it previously asserted, so anything that
disappears while it is down is never retracted. The other events in the list came back
`DUPLICATE_NOOP`, correctly — but silence about a deletion is not the same as a no-op.

**No gap.** The checkpoint carries no `gap_before`, and `aisre extent` reports `GAPS 0` for
`k8s:kind` across the hole. The mechanism is in `internal/feeders/k8s/feeder.go`:

```go
// noteResync records that an initial list completed and reports whether the feeder was blind
// before it. The first sync of a process is not a gap: the extent starts where the watch did.
func (f *Feeder) noteResync() bool {
	f.state.resyncs++
	return f.state.resyncs > 1
}
```

The counter is process-local. A feeder that was stopped and started again is a new process with
a resync count of zero, so its first checkpoint says "no gap" — which is exactly the case that
*is* a gap. Detecting it means comparing the new extent's start against the last checkpoint the
**graph** holds for this source; the feeder has that information available at registration and
does not ask for it.

**Consequence for T067.** `fixtures/feeder-gap-01` is shipped, and it is a faithful recording,
but it records the bug rather than the behaviour. Its goldens are a regression baseline: when
the feeder reconciles and reports its gap, they must change, and that diff is the evidence. The
manifest says all of this at the top, where a reviewer will see it. **T067's verification
clause — "verify retraction valid_end inside gap and observed at reconnection" — is not met,
and the task is left unticked.**

> **Corrected 2026-09-17: fixed, and the goldens did change.** The Kubernetes feeder now
> notices its own gap. `--state-dir` holds the last checkpoint it emitted and the objects it had
> asserted; the informers push that as a `start` marker before the initial list; the
> reconnection diffs the new list against it, retracts what has disappeared and emits a
> checkpoint carrying `gap_before` (`internal/feeders/k8s/state.go`, `Feeder.reconcile`,
> `Feeder.gapBefore` — the resync counter this section quotes is gone, replaced by a comparison
> against durable state rather than a process-local one).
> `fixtures/feeder-gap-01/golden/extent.extent.json` shows exactly one gap for `k8s:kind`,
> `[10:43:42.722705Z, 12:00:16.519Z)`, and none for `otel:kind`;
> `k8s.service=shop/checkout` is bounded at the reconnection with its observed interval starting
> there, and the `exposed-via` edge into it is closed with `closed_as_consequence_of`. One
> deviation is stated in the manifest: the retraction's valid end is the gap's upper bound
> rather than an instant strictly inside it, because `RetractNode` carries no `end_unknown` and
> the schema is frozen for this phase — the `gap_before` checkpoint beside it is what says the
> truth lies in the hole. **T067 is ticked.**

## The baseline, against the fixture it replaced

`fixtures/baseline-topology-01` was hand-authored (63 events, `k8s:demo` and `otel:demo`, a
`shop-prod` cluster). It is now a recording of a kind cluster. What changed, and why:

- **Source ids** are `k8s:kind` and `otel:kind`.
- **The cluster is `sre-agent-demo`**, not `shop-prod`. The README predicted this.
- **Two node pools, not one.** The feeder sees both kind nodes, so `control-plane` and
  `general` are both INFRA_RESOURCE nodes; `sre.k8s.node_count` is 1 for each, not 6.
- **The node-pool pointer selector is `v1/nodes?labelSelector=sre.node_pool%3Dgeneral`**, the
  feeder's default label, where the fixture used `node-pool`. `cluster.yaml` sets both labels
  on purpose, so this is a configuration difference, not a disagreement.
- **Six workloads, not four.** `redis` (a StatefulSet) and `payments-db` (a Deployment) are in
  the overlay so that more than one workload kind is exercised (FR-043). They do not merge with
  the telemetry nodes of the same name: neither carries a
  `resource.opentelemetry.io/service.name` annotation, deliberately, so `redis` and
  `payments-db` each appear twice — once as the workload Kubernetes reports, once as the third
  party the callers address. This is additive, and it is what the overlay says it wants.
- **`kube-root-ca.crt` is a CONFIG node.** Kubernetes puts that ConfigMap in every namespace;
  a feeder scoped to a namespace sees it. Nothing depends on it, so it never appears in
  `checkout`'s neighbourhood.
- **Real digests.** `sre.config.value_hash` is a SHA-256 of the ConfigMap's content, not a
  literal; the Secret's `sre.config.version` is its resourceVersion (`573`), not a rotation
  counter Kubernetes does not keep.
- **Event ids carry real resourceVersions** (`@rv999`, `@rv1063`), and every id is a pure
  function of the object it describes. The forty-entry `knownDivergences` table in
  `internal/feeders/k8s/feeder_test.go` existed only to excuse the hand-authored file's
  single-counter numbering; it is now empty, which is what its own comment said would happen.
- **Weight classes are 2 and 1**, not 4, 3 and 2 — see finding 4.
- **Timestamps carry microseconds.** A hand-authored fixture uses whole seconds; a recording
  uses what the source said.
- **`sre.k8s.revision` is 1** on a cluster that has rolled nothing out yet.

Not changed: the query set, the merge behaviour (certain rule C2, four merges), the
`redis-3hop-cap5` truncation, the empty-and-flagged before-history answer, and the
`rejected.jsonl` telemetry-payload refusal.

## SC-010: live versus recorded

The claim is that the graph built live equals the graph built from the recording. The test:

1. Both feeders ran against `live_baseline`, a database that had never held these events, and
   ingested them over HTTP as they happened.
2. At the end, `query subgraph otel.service.name=checkout --as-of <clock.end> --hops 2 --output
   json` was captured from that live server.
3. `fixture record` replayed `events.jsonl` into a *different*, empty database and wrote
   `golden/subgraph.checkout-2hop.json`.
4. The two were compared.

```
live: 20 nodes 27 edges
rec : 20 nodes 27 edges
byte-identical: True
```

**Byte-identical** — entity ids, valid intervals, observed times, the extent block and its
per-source checkpoints included. Not "identical up to timestamps": the same bytes. The
observed times match because the recorder writes the observed time the *graph* assigned at
acceptance rather than a clock of its own (`record.observedAtOf`), and replay applies each
event with that value rather than with the replay clock (FR-023).

That is SC-010 and FR-050 (b) for the baseline. The three scenario fixtures were recorded the
same way and verify from empty, but their live captures were not taken — the parity claim rests
on the baseline.
