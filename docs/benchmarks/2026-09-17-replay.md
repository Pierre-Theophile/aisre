# Replay at the reference workload — 2026-09-17

This closes the open finding of [`2026-09-16-scale-10k.md`](2026-09-16-scale-10k.md): a full
replay of a 1M-event log did not meet the ADR-0002 exit criterion, and the run that found it was
stopped rather than carried to a number.

**It does now. 995 222 events replayed into an empty projection in 37 min 44 s — 440 events/s —
at 500 events per transaction.** The ADR-0002 gate is 60 minutes and is met with 22 minutes to
spare. plan.md's 30-minute performance goal is missed by about 8 minutes; it is a goal, not a
gate, and the last section says where the remaining time is.

| | events | wall time | events/s | verdict |
|---|---:|---:|---:|---|
| 2026-09-16, one transaction per event | 638 471 of 969 459 entity versions, run abandoned | 4 h 29 min and still at 66% | ~39 | **ADR-0002 missed** (~4.5×), plan goal missed (~9×) |
| 2026-09-17, 500 events per transaction, unbounded page read | 175 000 of 995 222, run abandoned | 12 min 16 s at 238 events/s | ~238 | would have missed ADR-0002 (~70 min projected) |
| **2026-09-17, 500 events per transaction, `LIMIT`ed page read** | **995 222** | **37 min 44 s** | **440** | **ADR-0002 met** (< 60 min), plan goal missed (< 30 min) |

Reproduce with:

```sh
aisre fixture bench --db "$PG_DSN" --scale 10k --seed 1 --replay-only
```

## Environment

| | |
|---|---|
| CPU | Apple M5, 10 logical cores |
| Memory | 16.0 GiB |
| OS / arch | darwin / arm64 |
| Go | go1.27.1 |
| PostgreSQL | 16.13 (`postgres:16-alpine`, Docker compose, same host) |
| workload | scale `10k`, seed 1 — 995 222 events over 90 days |
| batch size | 500 events per transaction (`--replay-batch`, default) |

**Caveat, and it is not a small one.** A second agent was running `fixture verify` over all eight
fixtures and `go test ./...` against the same PostgreSQL instance and the same ten cores for most
of this run. Both compete for CPU and for the shared buffer cache, so the number above is a
*loaded* machine's number. That makes it a conservative one — an idle machine will not be slower
— but it also means the deceleration in the second half (1 050 events/s over the first 100 k,
440 events/s cumulative at the end) cannot be attributed entirely to the growing graph. A clean
re-run on an idle host is worth doing before anyone quotes the figure as a baseline.

## What changed

### 1. One transaction per event → 500 (the finding of 2026-09-16)

`Projector.Replay` opened a transaction per event, so a million events were a million commits.
`Projector.ReplayWithOptions` now takes a `BatchSize` and applies that many events per
transaction; `Replay` is the default-options wrapper, and `BatchSize: 1` restores the old loop.

Nothing about *what* a replay produces changed, and that is the part that had to be proved rather
than asserted. FR-023 is about the same events, in the same append order, each applied with the
observed time recorded on its own log row; the batch size only decides when the work is
committed. `internal/projector/replay_batch_test.go` replays **every shipped fixture at batch
sizes 1, 7 and 500** and requires byte-identical canonical snapshots and identical
`produced_by_event_ids`. Constitution III's "one event at a time" is about incremental
application — no batch rebuild from a source system, no truncate-and-reload, no folding several
events into one write — and it still holds: each event is applied on its own, against the state
its predecessors produced.

The cost is stated rather than hidden. **A failing event fails its whole batch**, so a replay
that dies part-way leaves the projection at the last committed batch boundary rather than at the
last event. That is acceptable precisely because a replay is not a live path: it rebuilds into an
empty projection, and the remedy for a failed one is to run it again from empty, never to resume
in place. `Apply`, which *is* the live path, is still one event per transaction.

### 2. The page read had to be `LIMIT`ed, and this is where most of the win was

Batching alone took the replay from ~39 to ~238 events/s — a projected 70 minutes, still a miss.
Sampling `pg_stat_activity` at 10 Hz against the running replay said why, and it was not where
anyone would have looked:

| samples (of 400) | statement |
|---:|---|
| 254 (63%) | `SELECT … FROM log.events WHERE appended_seq > $1 ORDER BY appended_seq` |
| 66 (17%) | the identity-claim scan behind the probable resolution rules |
| 16 | `autovacuum: ANALYZE graph.entity_versions` |
| 6 | `graph.close_observed()` |
| 5 | `INSERT INTO graph.entity_versions` |

**The hottest statement in the apply path was not in the apply path.** It was the replay's own
paged read of the log. The first implementation called `log.Iterate` and stopped the callback
after 500 rows — but the driver drains a result set when its rows are closed, so every page paid
for the entire rest of the log. A linear replay had become a quadratic one.

`EXPLAIN (ANALYZE, BUFFERS)` on the two shapes, at `appended_seq > 500000`:

```
LIMIT 500:   Index Scan using events_appended_seq_key  rows=500     Buffers: hit=38 read=2
             Execution Time: 0.147 ms

no LIMIT:    Index Scan using events_appended_seq_key  rows=495222  Buffers: hit=7376 read=24582 written=1994
             Execution Time: 98.609 ms
```

0.15 ms against 98.6 ms of server time — and the client side is worse, because those 495 222 rows
carry their payloads over the wire only to be discarded. Two thousand pages of that is the 63%.

The fix is `log.Page`, which is `log.Iterate` with a `LIMIT`, and the replay reads through it.
**No index was added**: the index the plan wants, `events_appended_seq_key`, already existed and
was already being chosen. Throughput went from 238 to 440 events/s overall, and to ~1 050
events/s over the first 100 k events, when the projection is still small.

## Where the remaining time is

The replay decelerates: ~1 050 events/s over the first 100 k, ~440 events/s averaged over all
995 222. Some of that is the concurrent test run on the same machine; the rest is the projection
growing under it — the final graph holds 969 459 entity versions, 404 068 edge versions, 60 000
entities and 258 800 identity claims in 2 247 MB, and every upsert reads the current versions of
the entity it touches before it writes.

The next statement to look at, if the 30-minute goal is ever made a gate, is the one the sampler
put second. `claimStore.ClaimsInNamespaces` scans `graph.identity_claims` for the probable
resolution rules, which compare *normalized* names and therefore cannot be served by an index on
`value`. Against the finished 258 800-claim projection:

```
Gather Merge (actual time=119.585..124.826 rows=7700 loops=1)
  Buffers: shared hit=29617 read=5747 written=1008
  ->  Parallel Bitmap Heap Scan on identity_claims c   (Bitmap Index Scan on identity_claims_ns_value_idx)
  ->  Nested Loop -> Index Scan using events_pkey on events e  (loops=7700)
```

125 ms and ~35 000 buffers per call at the end of the run, on ~17% of the samples. The fix is the
one `refs.go` already names — store the normalized name in a column of its own, so the rule can
be answered by an index instead of by a scan — and it is a schema change, not an index, so it is
deliberately **not** done here. Adding an index to the current shape would not help: the scan is
already index-driven, and the cost is the 7 700-row nested loop into `log.events` behind it.

## Verdict against the published criteria

| source | criterion | target | measured | result |
|---|---|---|---|---|
| ADR-0002 | full replay of the event log | < 60 min | **37 min 44 s** | **pass** |
| plan.md | replay of the event log | < 30 min | 37 min 44 s | missed (goal, not a gate) |

Missing an ADR-0002 criterion is what would reopen the storage decision under constitution X.
This one is met, and the two that were already met — the 2-hop subgraph and 24 h diff p95s — were
not re-measured by this run (`--replay-only` skips them; the report marks them *not measured*
rather than passed). **The storage decision stays where ADR-0002 put it**, and the reason the
replay criterion was missed on 2026-09-16 is confirmed to have been the replay loop rather than
PostgreSQL: the same events, the same store, the same indexes, 26× faster.
