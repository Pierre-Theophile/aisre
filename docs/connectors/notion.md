# The Notion connector

Written for the **workspace administrator** who creates the Notion integration and shares databases
with it, and the operator who runs `aisre feed notion`.

The connector registers the pages of the Notion databases an operator names (postmortems, runbooks)
as knowledge documents in the graph, linked to the services they concern. An investigation can then
cite "the checkout postmortem of 2026-05-14" when it looks at checkout. The connector reads page
titles, up to three named summary properties, one named property that says which services a page
concerns, and the page's dates. Since feature 008 it also reads the named `index_properties` and the
page body, and sends them, sanitised and cut into sections, to the agent's knowledge store, so a
search finds a postmortem by what it says rather than by its summary alone (§4a). It never reads a
people property, a comment or an attachment, and never writes anything to Notion.

**Status: experimental.** Its fixtures are generated by the real poller over a scripted twin, not
recorded from a real workspace, so by the [connector checklist](./checklist.md) it is not yet
stable. A real workspace was recorded on 2026-10-15 (007 T030) and replays under every corpus gate,
but that recording keeps titles and section text, as §7 says, so it stays in the private corpus and
cannot be the public fixture the checklist asks for.

Specification: [`specs/007-notion-knowledge/`](../../specs/007-notion-knowledge/spec.md), and for page
bodies [`specs/008-postmortem-rag/`](../../specs/008-postmortem-rag/spec.md).
Contract: [`contracts/notion-connector.md`](../../specs/007-notion-knowledge/contracts/notion-connector.md).

## 1. The integration, and what it is shared with

1. In Notion, **Settings → Connections → Develop or manage integrations → New integration**. Make it
   an **internal** integration in the workspace whose databases you will name.
2. Under **Capabilities**, tick **Read content** and nothing else: no Update content, no Insert
   content, no comment capability, and **No user information**.
3. Copy the secret (`ntn_…`) into `SRE_AGENT_NOTION_TOKEN` on the host that runs the connector.
4. Open each database the connector should read and **… → Connections → add the integration**. The
   integration sees exactly what is shared with it; sharing a database is what puts it in scope.

Notion does not report an integration's capabilities through its API, so the connector cannot check
step 2 itself. The operator states it instead: the configuration must carry
`acknowledge_read_only: [notion.capabilities]`, or `feed notion` exits with code 3 before any call.
The run records its credential evidence as `operator_asserted`, which is what it is (ADR-0013
item 4). What the connector **can** prove is the list of requests it is able to make, below.

At start the connector reads `GET /v1/users/me` and refuses to run if the integration's workspace name
is not the `workspace` label in the configuration, so a secret from another workspace cannot feed this
source.

## 2. The published read-only operation surface

Every request the connector can make. An operation absent from this list is refused by the issuer
before it leaves the process, and the attempt is recorded. The data-source query is a `POST` because
Notion puts the filter in the body; it is declared as a **named query** with the reason it changes
nothing, and `PUT`, `PATCH` and `DELETE` are refused whatever is declared.

| area | operation | why |
|---|---|---|
| auth | `GET /v1/users/me` | the integration's own bot user, whose workspace name is checked against the configured label (FR-003) |
| binding | `GET /v1/databases/{id}` | a configured database's title and data sources, to resolve the binding at start (FR-010, research R5) |
| pages | `POST /v1/data_sources/{id}/query` | named query: Notion documents it as returning the pages of a data source that match a filter and sort; its body carries only filter, sorts, start_cursor and page_size, and no field creates, updates or deletes anything (FR-040) |
| pages | `GET /v1/pages/{id}` | one registered page no longer returned by its data source, read once to tell trashed or moved from gone (FR-043) |
| pages | `GET /v1/pages/{id}/properties/{property_id}` | the rest of a named summary or entity property cut at 25 references in a query result (research R7) |
| bodies | `GET /v1/blocks/{id}/children` | the body of a registered page whose last_edited_time moved, 100 blocks per call, to depth 3 and at most 1,000 blocks (008 FR-010, research R6) |

**The table above and the code are one list.** It lives in
[`internal/notionx/client.go`](../../internal/notionx/client.go), and a test parses this page and
compares it with `notionx.Surface` in both directions. This surface is **enforced**: the client has no
other path to the network.

## 3. Configuration

```yaml
workspace: acme                     # the label in the source id, notion:acme; must be the integration's workspace name
principal: oidc:riley@example.com   # who signs this configuration; recorded as configured_by
acknowledge_read_only: [notion.capabilities]
poll_interval: 15m
reconcile_every: 24h
databases:
  - database: 0a1b2c3d4e5f60718293a4b5c6d7e8f9
    kind: postmortem                # postmortem | runbook
    entity_property: Services       # select, multi-select, status or relation
    summary_properties: [Summary, Root cause, Resolution]   # at most 3: title, rich text, select or status
    authored_property: Incident date                       # optional date; else the page's creation time
    index_properties: [Summary, Signals / Symptoms, Root cause, Resolution]  # sections; no limit; default: summary_properties
    index_body: true                                       # the page body, by heading; default true
  - database: 1b2c3d4e5f60718293a4b5c6d7e8f90a
    kind: runbook
    entity_property: Service
    summary_properties: [Purpose]
```

Every page whose entity property carries a value is registered with its values
(`sre.notion.values`), and the [service catalog](../../specs/009-service-catalog/spec.md) decides
which service it concerns: a value the catalog has an alias for is attributed to that entry, and a
value it does not know is proposed as one (`aisre catalog proposals`). Nothing in this file says
what a value means.

**Deprecated: the `entities` map.** Before the catalog, each binding mapped values to graph entities
itself:

```yaml
    entities:                       # deprecated: value → graph entity; for a relation, keys are related page ids
      Checkout: k8s.service=checkout
```

A binding that still has one keeps working as it did in 007: a page is registered only when its
entity property carries a value the map names, and is linked by the map rather than by the catalog.
Move the map into the catalog once, then delete it from this file:

```sh
aisre catalog import --from-notion-config notion.yaml --dry-run   # what it would record
aisre catalog import --from-notion-config notion.yaml
```

Each line becomes an entry named after the value, with two aliases: `notion.value=<database>/<value>`
and the entity the line named. The map will be removed in a later version.

## 4. What is registered

Each page becomes one `KNOWLEDGE_DOC` node, `notion.page=<page id>`, with:

| prop | value |
|---|---|
| display name | the page's title, plain text |
| `kind` | the binding's kind |
| `summary` | the named properties, plain text, joined with ` — `, at most 600 characters (`summary_truncated` says when cut) |
| `location` | the page's URL |
| `authored_at` | the named date, else the page's creation time |
| `registered_by` | `notion:<workspace>` |
| `configured_by` | the configuration's `principal` |
| `link_provenance` | `notion/notion-db@1 configured by <principal>` |

and one `CONCERNS` edge per mapped value, carrying `rule`, `database`, `property` and `property_value`: the
clause that made the link. A user mention inside a summary property is removed before anything is
stored.

**Time.** A page's links are valid from its creation time when it is first registered, and from its
`last_edited_time` for every later change. A value removed from the entity property ends its link at
the edit that removed it. A page moved to the trash, archived or moved out of the database ends all
its links at its last edit; a page that answers 404 ends them at the last instant the connector saw
it. The node itself is never deleted, so an investigation replayed as of an earlier instant still
cites what was true then.

**When it is read.** Every `poll_interval` (default 15 minutes) the connector queries each data source
for pages edited since the last poll, less two minutes of overlap. At start and every
`reconcile_every` (default daily) it lists every page and reads, once each, the registered pages the
list no longer returns. A database that cannot be read is a coverage gap: nothing is retracted for it.

## 4a. What is indexed (feature 008)

The graph says which pages exist, what they concern and when; what they say goes to the agent's
knowledge store, outside the graph, through `KnowledgeService.PutSections` on the same server and
under the same feeder token. A token for `notion:<workspace>` may write only `notion.page=` documents.

A page's **sections** are:

- each `index_properties` property with text, one section labelled with the property's name;
- the body, one section per heading (levels 1 to 3) labelled with the heading's text; text before the
  first heading is the section `Body`. Paragraphs, list items, to-dos, quotes, callouts, toggles,
  code and table rows are read, children included to depth 3, at most 1,000 blocks per page.
  A child page, a child database, a link to a page, a synced block from another page, embeds,
  files, images and bookmarks are not read, and are counted in the report.

A section over 1,200 characters is split into parts, each keeping the label. Before anything is
split, stored, recorded or logged, every label and text is sanitised: user mentions are dropped
when the text is built, and e-mail addresses, @handles and the secret shapes the commit scan
refuses become `[redacted]`. A section nothing is left of is skipped with the reason `emptied by
sanitisation`.

The body is read only for pages whose `last_edited_time` moved since it was last read, so an
unedited database costs nothing beyond the 007 poll. The whole current set is sent each time: an
unchanged section is a no-op, a changed one opens a new version, and a section that disappeared is
closed, so a search as of an earlier instant reads what the page said then. A page that is trashed,
moved or deleted has its sections closed with its links.

How those sections are ranked, which store keeps them and how to add an embedding model (hosted or
self-hosted) is in [the retrieval guide](../knowledge/retrieval.md).

## 5. What it costs

Notion allows an average of three requests per second per integration and reports nothing about what
is left. The connector spends at most three calls in each second (`static_fallback` in its usage
report) and waits for the next second rather than failing. A `429` closes the budget until the instant
Notion's `Retry-After` names; if that is more than 30 seconds away the poll is cut short and reported
as a coverage gap, never as "no pages".

Reading a body costs one call per 100 blocks, plus one per toggle, column or table with children,
and only for pages edited since their last read: a database of a few dozen typical postmortems is
a few dozen calls the first time and nothing after.

## 6. Running it

```sh
export SRE_AGENT_NOTION_TOKEN=ntn_…
aisre feed notion --config notion.yaml              # poll and reconcile until stopped
aisre feed notion --config notion.yaml --once       # one reconciliation, then exit
aisre feed notion --config notion.yaml --check      # read everything, send nothing, print the report
aisre feed notion --config notion.yaml --record dir # also record the sanitised exchange
aisre feed notion --config notion.yaml --replay dir # read a recording instead of Notion
```

`--state <file>` (default `notion-state.json` beside the configuration) is where the connector keeps
what it registered, so that a restart can still notice a page that disappeared while it was stopped.

`--check` reads every configured database once, sends nothing to the graph and never writes the
state file. Per database it prints the data sources it read, whether each configured property was
found on any page (a property found on none is usually a typo or a renamed column), the pages
registered and each page not registered with its reason, the pages that ended, and how many listed
pages live outside the configured databases (a count only). It also says what the integration's
capabilities rest on: Notion cannot be asked, so it is the configuration's acknowledgement. Since
008 it also reads every registered page's sections, whether or not they were read before, and
prints per page each section's label, origin and size, then what was skipped and why. Page titles
and section labels are printed; summaries and section text never are. The same report, as counts
plus each page not registered, is logged at the end of every reconciliation.

```text
database 0a1b2c3d-4e5f-4071-8293-a4b5c6d7e8f9 (postmortem)
  data sources: 2c3d4e5f-6071-4293-a4b5-c6d7e8f90a1b
  property "Services" (entities): found
  property "Resolution" (summary): NOT FOUND on any page; check the spelling
  registered: 1
    "Payments pool exhaustion"
  not registered: 1
    "Vendor bridge outage": unmapped value Search
  sections read: 1 page(s)
    "Payments pool exhaustion": 4 section(s)
      Summary (property, 77 chars)
      Signals / Symptoms (property, 1035 chars)
      Timeline (body, 1538 chars, 2 parts)
      Detection (body, 193 chars)
      skipped Contact: emptied by sanitisation
      skipped unsupported block embed: 1
```

The reasons a page is not registered are a closed set: `no mapped entity`, `unmapped value <v>`,
`in another bound database <id>` and `untitled`. A trashed, moved or deleted page is counted as ended.
The reasons something of a page is not indexed are too: `emptied by sanitisation`, `over 1,000
blocks; truncated`, `over 500 sections; truncated` and `unsupported block <type>`, counted per type.

Exit codes are the CLI's: 0 ok, 1 usage or configuration, 2 Notion unreachable at start, 3 the
credential refused or the acknowledgement missing.

## 7. Recordings

A recording (`--record`) is sanitised before anything reaches disk (FR-050): page, database,
data-source and workspace ids are pseudonymised; the page URL is dropped (a replay rebuilds a URL
from the pseudonymised id); titles, summaries and mapped values are kept, because they are what
retrieval ranks and what the map reads, and so are section labels and text, already sanitised as §4a
says. People never enter a payload: the connector does not decode `created_by`, `last_edited_by` or
people properties at all. A recording of a real workspace stays private; the public repository
carries only the synthetic twins
[`fixtures/notion-knowledge-twin-01`](../../fixtures/notion-knowledge-twin-01/manifest.yaml) (registration)
and [`fixtures/notion-knowledge-twin-02`](../../fixtures/notion-knowledge-twin-02/manifest.yaml) (sections).
