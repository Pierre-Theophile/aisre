## Why Phase 2 is unusually large, and must not be skipped

[research.md §1](./research.md) checked the six contract items the spec asks of feature 001 against
the code as merged. **Four are real work, and one of them — a certain rule for a shared deploy
identifier — gates SC-004, the property this whole feature exists to deliver.** Feature 003 shipped
C4, C5 and C7 without a cross-source fixture and all three were published, registered, evaluated on
every claim and **never fired**; two had defects that only such a fixture exposed. So the rule and its
cross-source fixture are built **together, in Phase 2**, before either connector emits anything.

## Phase 3: User Story 1 — A GitHub deployment is a change, and it is the same change the platform saw (Priority: P1) 🎯 MVP

**Goal**: a completed GitHub deployment becomes a ROLLOUT change per target, valid at the platform's
completion instant, carrying actor, actor kind, an origin link and the deploy claims — and merging
with the platform feeder's observation of the same rollout rather than sitting beside it.

**Independent Test**: replay recorded workflow-run, deployment and `deployment_status` payloads from
an **empty** graph and compare change nodes, targets, actors, actor kinds, valid times and claims to
goldens; then replay the same window together with the platform feeder's recording and confirm the
ranked change list contains the rollout **once**.

**What a tick means in this phase, stated rather than left to be inferred.** Every task below names a
fixture, and none of those fixtures exists yet — T073–T079 build them and **T080 is the gate that
replays them against goldens**. So a task is ticked here when its logic is implemented and verified by
assertions that can fail, and T080 stays open until the recorded corpus exercises the same logic
end to end. That is a different thing from Phase 2F's ten tasks, which T141 moved rather than ticked:
those could not be *written* without a fixture (they assert properties of a recorded window), whereas
